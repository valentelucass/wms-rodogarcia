# D27 — contrato da testemunha simultânea

Nova fixture exclusivamente HTTP/D27, JAR novo. Cedro publicará `d27-concorrencia-pedido.json` nesta pasta com rodada/cliente/armazém/produto/pedidos/appPID antes de qualquer gate. Prumo prepara observador SELECT próprio, sem conceder DMV à app, e publica `orchestracao/.runtime/d27-prumo-concorrencia-pronto.json` com `rodada` igual, `pronto=true`, `observadorAtestado=true`, `banco=WMS_DEV`, `servidor=ROD-SRVW-001`. Ausência/divergência não libera o gate; falha18456 fica comprovada e separada.

Após readiness, Cedro publica fase `gate-ativo`: SELECT com UPDLOCK/HOLDLOCK na linha cliente em conexão WMSDEV própria, sem DML. Duas reservas HTTP integrais de80 sobre saldo100 aguardam essa linha. Prumo captura duas requisições SQL bloqueadas e publica o mesmo recibo readiness com `duasRequestsBloqueadas=true` e `evidenciaSQL` relativo público. Cedro libera imediatamente após o sinal, limite15s para evitar timeouts artificiais. Resultado esperado conjunto200/409, um pedido RESERVADO integral80 e outro RASCUNHO/zero reservas; GET/replay/saldo, sem reset. Toda resposta passa pelas mesmas guardas cookie/request-id/segredo, nunca valores de cookie ou token em evidências.

Se não houver duas requisições observadas, gate é liberado no prazo, rodada permanece sem prova witness; par200/409 isolado não certifica simultaneidade SQL. Prumo guarda amostra/horários/SPIDs/bloqueador; nenhum SQL Cedro para alteração de dados ou inspeção administrativa. Relatórios vinculam IDs exatos, não ponte genérica a outras APIs. Comunicação apenas por arquivos, sem callback.
